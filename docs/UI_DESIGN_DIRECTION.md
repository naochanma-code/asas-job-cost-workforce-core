# ทิศทางดีไซน์ ASAS Core

สถานะ: **DESIGNED_REFERENCE** · Owner ส่งภาพอ้างอิง 5 ภาพ วันที่ 24 กันยายน 2026 · ยังไม่ใช่หน้าจอที่พัฒนาแล้วหรือผ่าน UAT

เอกสารนี้แปลงภาพอ้างอิงเป็นแนวทางสำหรับ Web แต่ละ milestone โดยยึด [MASTER_PROMPT](MASTER_PROMPT.md), [WIREFLOWS](WIREFLOWS.md), [PERMISSION_MATRIX](PERMISSION_MATRIX.md) และสถานะจริงใน [PROJECT_STATUS](PROJECT_STATUS.md) เมื่อมีรายละเอียดขัดกัน ภาพเป็นตัวอย่างรูปลักษณ์ ไม่ใช่การอนุมัติ feature, ตัวเลข, permission หรือข้อมูลตัวอย่างในภาพ

## ภาษาภาพรวม

- แถบเมนูซ้ายยึด **ภาพที่ 1**: พื้นถ่านเข้มเกือบดำ, ตัวอักษร/ไอคอนสีขาว, รายการที่เลือกเป็นแดงเข้ม และองค์ประกอบแบรนด์สีแดงเท่าที่ช่วยบอกตำแหน่ง ไม่ใช้พื้นแดงในพื้นที่เนื้อหาทั้งหน้า
- พื้นที่เนื้อหากลางยึด **ภาพที่ 2–5**: พื้นหลังขาวอมฟ้า, ตัวอักษรสีน้ำเงินเข้ม, ปุ่มหลัก/ลิงก์สีน้ำเงิน, การ์ดขาวขอบบางและมุมมน ตารางและตัวกรองโปร่ง อ่านง่าย
- ลำดับชั้นข้อมูล: ชื่อหน้าและคำอธิบายสั้น → ตัวกรองที่เกี่ยวข้อง → ตัวเลข/งานที่ต้องทำ → รายการหรือกราฟที่กดไปยังต้นทางได้ ใช้สีสถานะร่วมกับข้อความเสมอ
- ปุ่มหลักเป็นน้ำเงิน; เขียวใช้ผลสำเร็จ/อนุมัติ; เหลืองใช้รอตรวจ/ข้อมูลยังไม่ครบ; แดงใช้ข้อผิดพลาด/ปฏิเสธ ไม่สื่อสถานะด้วยสีอย่างเดียว
- ภาษาไทยเป็นหลัก ชื่อ Project/Job และรหัสแสดงเต็มเท่าที่พื้นที่เอื้อ อัตราส่วนเงินใช้สกุลบาทและเครื่องหมายหลักพัน วันที่และเวลาอ้างเขตเวลาไทย
- Desktop ใช้เมนูซ้ายและ top bar แบบภาพ; มือถือยุบเมนูเป็นปุ่มเปิด/ปิด, วางการ์ดเรียงแนวตั้ง, เปลี่ยนตารางกว้างเป็นรายการที่อ่านได้โดยไม่ต้องซูม ปุ่มสำคัญกดง่ายและมีข้อความตอบกลับอยู่ใกล้ฟอร์ม
- ทุกหน้าต้องมีสถานะ loading, ไม่มีข้อมูล, error/retry และผลหลังบันทึก ไม่ใช้ค่าตัวอย่างเป็นข้อมูลจริงหรือแสดงกราฟจากข้อมูลที่ยังไม่มี

## หน้าตามบทบาทและ flow

| ภาพอ้างอิง | หน้าปลายทาง | ขอบเขตข้อมูลและการทำงาน |
| --- | --- | --- |
| 1 + 2 | Owner Financial Dashboard | ใช้เมนูซ้ายจากภาพ 1 และเนื้อหาจากภาพ 2; รายได้ ต้นทุน งบ Actual กำไร Margin Forecast และ drill-down เฉพาะ OWNER เมื่อ financial ledger/ข้อมูลต้นทางพร้อม ตัวเลข pending ไม่รวม Actual และต้นทุน Hardware จาก SMEMOVE ต้องแสดงสถานะความครบถ้วน |
| 3 | Admin Operations Dashboard | Project ที่กำลังทำ, งานรอตรวจ Work/OT/Expense, ทีมที่ลงงานและงานล่าช้า ใช้ข้อมูล operational; ห้าม query หรือส่งยอดรวมต้นทุน/กำไร/ค่าแรงเข้า browser ของ ADMIN |
| 4 | Project detail | หัวโครงการพร้อมลูกค้า/Site/PM/สถานะและความคืบหน้า; แท็บ Jobs แสดงจำนวน รายการ และปุ่มเพิ่มชัดเจน; ไม่มี Job ให้ทำงานระดับ Project ได้โดยไม่ถาม Job; แท็บอื่นเปิดเมื่อ flow นั้นใช้งานจริง |
| 5 | Expense review | ADMIN/OWNER เห็นจำนวนเงินและหลักฐานระดับรายการ ตรวจ แก้ พร้อมเหตุผล อนุมัติหรือปฏิเสธ พร้อม audit; PM/TECH ไม่เป็นผู้ตรวจและ PM เห็นเฉพาะค่าใช้จ่ายของตน; รูปหลักฐานมาจาก Core private storage |

หน้ารวมโครงการต้องช่วยเปิด Project/Job ที่มีสิทธิ์ได้เร็ว แต่ข้อมูล Job เป็นลูกของ Project เสมอ จำนวนและสถานะในเมนู/การ์ดต้องคำนวณจากรายการจริงตาม scope ผู้ใช้ ไม่ hard-code ตามภาพตัวอย่าง

## การนำไปใช้ตาม milestone

1. **M1 Project/Job**: นำโครงหน้า, สี, ระยะห่าง, รายการโครงการ และ Project detail/Jobs มาใช้กับ flow ที่มี API จริงอยู่แล้ว ทดสอบ Owner/Admin/PM/TECH และ Project ที่ไม่มี Site/Job รวมมือถือก่อนเปลี่ยนสถานะ TESTED_UI ไม่เพิ่มเมนูการเงินหรือ Expense
2. **Work/OT และ Expense**: เพิ่มแท็บ/คิวตรวจเมื่อ create→review→approval→readback พร้อมสิทธิ์และ automated tests ผ่าน; สถานะรอตรวจไม่กลายเป็น Actual
3. **Owner Financial**: สร้าง Dashboard ตามภาพเมื่อ selling price, estimated/actual cost, ledger, completeness และสิทธิ์ OWNER ผ่านการทดสอบแล้ว แสดงที่มาของยอดและวันที่อัปเดต; ห้ามใช้ตัวเลขจำลองในหน้าจอใช้งานจริง

ภาพอ้างอิงเป็นไฟล์ local ใน `Picture/` ของ workspace; ไม่คัดลอกรูปที่อาจมีชื่อบุคคลหรือภาพบิลเข้า Git เอกสารนี้เก็บเฉพาะแนวทาง UI และข้อจำกัดข้อมูล

## เกณฑ์ตรวจรับ UI เมื่อพัฒนาแต่ละ flow

- ผู้ใช้หา action หลักได้จากหน้าแรกและทราบทันทีหลังบันทึกว่ารายการสำเร็จหรือผิดพลาด พร้อมเปิดรายการที่เพิ่งสร้างได้
- Desktop และมือถืออ่านเนื้อหา/สถานะ/ปุ่มได้โดยไม่ซ้อนทับหรือซูม ตารางที่กว้างต้องมีรูปแบบมือถือ
- ตรวจด้วยบัญชีจริงตามบทบาทว่าข้อมูลการเงินไม่หลุดไปยัง ADMIN/PM/TECH และข้อมูลข้าม Project ไม่ปรากฏ
- ภาพหน้าจอและ test evidence ต้องใช้ข้อมูลสมมติ แยก CODED, TESTED_LOCAL, DEPLOYED_STAGING และ UAT_PASSED ตามสถานะจริง
